# Phase 5 Checklist: CBD-Led CAR Review Platform

This checklist is the authoritative Phase 5 state ledger. Items are never
deleted; a checked item requires observable evidence. Supporting-repository
work remains part of Phase 5 only when it satisfies a CBD Support-owned Review
contract.

## Normative Contract

- [x] `P5-01` Stable design fixes CBD Support as the CAR Review product owner and Cozy, `sbt-cozy`, Textus AI, CNCF, SIE, catalog, runtime, and other AI integrations as attributable providers without competing canonical reports. Evidence: `docs/design/car-review-architecture.md`.
- [x] `P5-02` Static specification fixes versioned Review Provider descriptor, request, evidence-bundle, capability, rule-selection, limitation, digest, and compatibility contracts with representative canonical JSON. Evidence: `docs/spec/car-review-provider-contract.md`, `docs/spec/schema/car-review-provider-v1.schema.json`, representative JSON under `docs/spec/examples`, and `CarReviewProviderContractSpec`.
- [x] `P5-03` Static specification fixes canonical Review Report, Review Run, Finding, Assurance, Unknown, location, severity, confidence, disposition, applicability, maturity, coverage, provider, baseline, and attestation contracts. Evidence: `docs/spec/car-review-report-contract.md`, `docs/spec/schema/car-review-report-v1.schema.json`, representative Run/Report/attestation JSON under `docs/spec/examples`, and `CarReviewReportContractSpec`.
- [x] `P5-04` Security specification fixes target admission, path/process/network bounds, authorization, credential resolution, redaction, AI input, MCP exposure, retention, and deterministic/offline CI behavior. Evidence: `docs/spec/car-review-security-contract.md`, `docs/spec/schema/car-review-security-policy-v1.schema.json`, representative development/CI policies under `docs/spec/examples`, and `CarReviewSecurityContractSpec`.

## Review Application Core

- [x] `P5-10` CBD Support implements a canonical Review Report model and deterministic codec whose identity and digest are stable for equivalent normalized evidence. Evidence: `CarReviewModel`, `CarReviewReportCodec`, and `CarReviewReportCodecSpec` prove distinct value types, strict wire/model admission, canonical encoding, stable digest normalization, rejection behavior, and digest recalculation.
- [x] `P5-11` CBD Support implements Review Run command/query lifecycle through CNCF Job execution with authorized start, progress, cancellation, completion, failure, and limitation state. Evidence: `CarReviewRunModel`, `CarReviewRunCodec`, `CarReviewRunLifecycle`, `CarReviewRunApplication`, `CncfCarReviewJobGateway`, `CarReviewRunLifecycleSpec`, `CarReviewRunApplicationSpec`, and `ComponentFactorySpec` prove typed Run admission, stable Review-to-Job binding, role-specific start/read/cancel, actual CNCF Job submission and cancellation, lifecycle projection, terminal immutability, safe missing-report failure, read-only MCP publication, and private Review commands.
- [x] `P5-12` CBD Support admits provider bundles only after schema, capability, target, digest, and compatibility validation and preserves incompatible, unavailable, disabled, and failed providers as attributable Unknown or run failures. Evidence: `CarReviewProviderBundleAdmission`, `CarReviewProviderExecutionCoordinator`, `CarReviewProviderBundleAdmissionSpec`, and `CarReviewProviderExecutionCoordinatorSpec` prove strict v1 admission, provider identity preservation, timeout/cancellation/failure attribution, and request-digest duplicate execution prevention.
- [x] `P5-13` CBD Support reconciles Evidence and Observations without losing provider identity, fabricating Assurance, choosing an implicit source winner, or rerunning an already admitted provider bundle. Evidence: `CarReviewBundleReconciler`, `CarReviewAssessmentGateBuilder`, `CarReviewReportAssembler`, and their executable specifications prove attributable reconciliation, duplicate suppression, explicit conflicts, Assurance-to-Unknown protection, deterministic assessment/gate, and canonical report assembly.
- [x] `P5-14` Review Run persistence, retention, comparison, immutability, and baseline behavior preserve target/report attribution and reject stale or mismatched gate evidence. Evidence: `CarReviewRepository`, `CarReviewRepositorySpec`, and `docs/journal/2026/07/car-review-p5-14-retention-2026-07-16.md` prove atomic completed Run/Report attribution, immutable identity conflicts, finite per-target Run/Report retention, deterministic expiry, content-free deletion/expiry audit, stale-gate rejection, and target-matched retained baseline comparison.

## Provider Framework and Cozy

- [x] `P5-20` CBD Support implements provider registration, capability discovery, bounded invocation, timeout/cancellation, CallTree-safe observability, and limitation reporting through CNCF provider/driver boundaries. Evidence: `CarReviewProviderRegistry`, `CarReviewProviderExecutionCoordinator`, `CarReviewProviderExecutionApplication`, `CncfCarReviewProviderRunner`, and their executable specifications prove immutable strict registration, deterministic bounded discovery, exact descriptor-bound runner selection, timeout/cancellation/limitation handling, request-digest duplicate prevention, and CNCF ProviderCall execution with safe CallTree properties.
- [x] `P5-21` Cozy emits a generic `ReviewEvidenceBundle` for CAR/CML/model/build/package/ABI/documentation analysis with Cozy, rule-set, CML, CAR, and supported CNCF version identity. Evidence: Cozy `CozyCarReviewProvider` and `CozyCarReviewProviderSpec` prove CBD-neutral v1 descriptor/bundle emission, request/target/provider/rule-set digest binding, strict capability/evidence-kind/rule selection without fallback, deterministic project/CML/build/CAR package/lint-derived ABI/documentation evidence, declared CNCF versions, and explicit static-analysis, invalid-limit, input-byte, evidence-count, and observation-count limitations.
- [x] `P5-22` Cozy's existing CAR lint findings are preserved exactly through the provider adapter, and `cozy car lint` remains a focused independent command backed by the same rule results. Evidence: `CozyCarReviewProviderSpec` compares every adapted lint record's category, code, level, relative path, line, and message to `CozyCarLint.lint`, and proves the independent JSON command emits the same finding collection and its normal fail/no-fail exit policy.
- [x] `P5-23` CBD Support can invoke Cozy through the provider protocol for an admitted CAR while Cozy has no dependency on or call to CBD Support. Evidence: CBD `CozyCarReviewProviderRunner` binds an admitted target before invoking a bounded `cozy review car-evidence` command transport; its specification proves registry-mediated single invocation, target-mismatch refusal before provider work, stdin-only request exchange, finite private response storage, and no inherited child environment. Cozy `CozyCarReviewProviderCommand` independently admits the v1 provider request and emits only the neutral evidence bundle without a CBD Support dependency.
- [x] `P5-24` Executable provider specifications prove compatible admission, incompatible refusal, explicit limitation, target-digest mismatch, cancellation, timeout, duplicate-bundle prevention, and provider-identity preservation. Evidence: `CarReviewProviderBehaviorMatrixSpec` exercises the exact v1 Cozy exchange across admission and execution coordination, proving compatible provider/limitation attribution, target-digest refusal without identity rewrite, cancellation, timeout, request-digest duplicate suppression, and exact provider identity preservation. Detailed boundary specifications remain in `CarReviewProviderBundleAdmissionSpec`, `CarReviewProviderExecutionCoordinatorSpec`, and `CozyCarReviewProviderRunnerSpec`.

## sbt-cozy CI/CD Bridge

- [x] `P5-30` `sbt-cozy` emits attributable generation, compilation, test, dependency-resolution, CAR-build, and task-result evidence without implementing CBD quality assessment. Evidence: `SbtReviewEvidence`, `cozyReviewSbtEvidence`, `SbtReviewEvidenceSpec`, and the `cozy/review-evidence` scripted fixture prove deterministic provider-v1 descriptor/request/bundle documents, source-content target digesting, bounded stable output, CAR-only build invocation, and explicit no-quality-assessment limitation.
- [x] `P5-31` `sbt-cozy` invokes Cozy locally, submits Cozy and sbt evidence bundles to the CBD Review Application, and receives one canonical report and gate result without granting a server arbitrary workspace access. Evidence: the `cozy/review-submit` scripted fixture and opt-in `scripts/probe-cbd-review-sbt-cozy.sh` run local Cozy `0.3.0-SNAPSHOT`, submit paired Cozy and sbt-cozy provider documents to the running CBD HTTP endpoint, and verify one CBD-owned canonical response and its local JSON/HTML/SARIF/attestation projections without a server workspace path or client-supplied role.
- [ ] `P5-32` Sbt Review tasks produce or obtain the canonical report, apply the CBD gate result, and materialize selected JSON, HTML, and SARIF projections with documented stable task and setting names.
- [ ] `P5-33` CI writes report, HTML, SARIF, and attestation artifacts under a stable target path, and attestation binds target digest, report digest, profile, providers, rule sets, and gate result.
- [x] `P5-34` Standard CI runs deterministic providers offline with external and AI providers disabled unless explicitly configured, and secrets never enter task output or Review artifacts. Evidence: `sbt-cozy` `SbtReviewCiPolicy`, `cozyReviewCiPolicy`, `SbtReviewCiPolicySpec`, and `SbtReviewReportArtifactsSpec` prove default local-only provider admission, loopback-only gateway execution, named opt-ins, invalid profile refusal, attestation-digest verification, and sensitive field/value refusal before any artifact write.
- [x] `P5-35` Any connection from a successful Review attestation to publish, distribution, or deployment is explicit and opt-in; existing sbt publication tasks retain their default behavior. Evidence: `sbt-cozy` `cozyReviewPublish`, `cozyReviewDistribute`, `reviewGatedTaskLabel`, and `CozyPublishVersionPolicySpec` prove that only named Review-gated CAR/SAR release tasks require `cozyReviewGate`, while ordinary publish/distribute task labels remain unchanged.

## Web, CLI, Report, and MCP Surfaces

- [x] `P5-40` The CBD Support CLI runs local and authorized server-backed Review through the same Review Application contract and returns stable run, report, gate, and exit behavior. Evidence: `CarReviewCliMain`, `CarReviewCli`, `CarReviewCliHttpTransport`, and `CarReviewCliSpec` prove local stdin/process-role submission and a real loopback private HTTP envelope exchange whose server-side adapter resolves authorization, with the same canonical run/report/gate result and stable pass/fail/unknown/error exit policy.
- [x] `P5-41` The Web UI displays Review Run progress, target/provider state, limitations, and completed report overview without deriving conclusions outside the canonical report. Evidence: authenticated Retrieval Web forms for `getReviewRun`, `getReviewSummary`, `getReviewReport`, `listReviewFindings`, `listReviewAssurances`, and `getReviewViews`; `ComponentFactorySpec` and `CarReviewRunApplicationSpec` prove form ownership, exact canonical response fields, report retention/readback, authorized lifecycle progress, provider state/limitations, and no Web-derived conclusion.
- [x] `P5-42` CNCF, implementation, and quality views project shared Evidence and Observation identities and support cross-view navigation to provider and implementation locations. Evidence: Retrieval `getReviewViews`, `CarReviewViewProjection`, `CarReviewMcpReadApplication.views`, `ComponentFactory`, `CarReviewViewProjectionSpec`, and `ComponentFactorySpec` prove the authorized Web/MCP surface returns all three canonical views with shared IDs, provider/rule/bundle attribution, and redacted implementation locations without provider reruns.
- [x] `P5-43` Text, canonical JSON, HTML, and SARIF projections are deterministic and consistent; SARIF remains an explicitly lossy location-bearing Finding projection. Evidence: `CarReviewReportProjection` and `CarReviewReportProjectionSpec` prove same-Report deterministic text/JSON/HTML/SARIF rendering, common Review/gate identity, HTML escaping boundary, and location-bearing-Finding-only SARIF with explicit omission count/policy.
- [x] `P5-44` Authorized, bounded, redacted queries can retrieve Review Run, summary, report, Finding, and Assurance information through MCP without exposing sensitive evidence or arbitrary report history. Evidence: Retrieval CML operations `getReviewRun`, `getReviewSummary`, `getReviewReport`, `listReviewFindings`, and `listReviewAssurances`; `ComponentFactory`, `CarReviewMcpReadApplication`, `ComponentFactorySpec`, and `CarReviewMcpReadProjectionSpec` prove runtime retention, read-only MCP publication, exact-Report addressing, role enforcement, 1–100 observation bounds, credential/facts/rationale/path redaction, and no history-list operation.
- [x] `P5-45` Review start, cancellation, retention administration, filesystem access, external-provider enablement, and AI-cost-bearing operations remain private to MCP unless an explicit later policy admits them. Evidence: `CarReviewMcpExposurePolicy`, `CarReviewMcpExposurePolicySpec`, and `ComponentFactorySpec` prove a fixed read-only allowlist, private-by-default/unknown behavior, explicit private operation categories, and actual CBD MCP exposure of retrieval read operations only.

## Quality, AI, and Runtime Assessment

- [x] `P5-50` Reusable capability definitions map one Evidence or Observation into multiple CNCF, implementation, and quality views without rerunning analysis. Evidence: `CarReviewCapabilityCatalog`, `CarReviewViewProjection`, and their executable specifications prove CBD-owned capability definitions reuse canonical Evidence/Observation IDs for CNCF, implementation, and quality projections without a provider invocation.
- [x] `P5-51` Applicability, maturity, coverage, confidence, provider attribution, strengths, gaps, and Unknown accounting are deterministic and do not collapse into an unexplained aggregate quality score. Evidence: `CarReviewQualitySummary` and `CarReviewQualitySummarySpec` prove sorted per-capability accounting retains the canonical Report's assessment identifiers, attributes, strengths, gaps, and Unknown references while exposing no aggregate score.
- [x] `P5-52` Security, Domain, Documentation, AI Readiness, Resilience, Testability, and Observability views have specified capabilities and executable representative assessments. Evidence: `CarReviewCapabilityCatalog` specifies each view's assessment focus and representative evidence kinds; `CarReviewCapabilityAssessment` and `CarReviewCapabilityAssessmentSpec` prove a mapped, attributable assessment for every capability and refuse unspecified capability IDs.
- [x] `P5-53` CBD Support AI Review uses Textus AI's provider-neutral `AiRunner`, structured `generateRecord`, and Review purpose profiles for admitted Gemma/Ollama, OpenAI, or Google Gemini execution; it receives only bounded structured evidence, remains opt-in, and contains no provider wire API, credential, or provider-specific response parsing. Evidence: `CarReviewAiRunnerAdapter`, `TextusAiCarReviewProviderRunner`, and their executable specifications prove a configured purpose-profile turns bounded Evidence into an admitted advisory provider bundle through the CBD registry/coordinator, retaining only a candidate digest and allowlisted execution facts. Concrete Textus AI runtime-field compatibility remains P5-55.
- [x] `P5-54` Runtime evidence is attributable and bounded, static analysis cannot claim `Operational`, and accepted runtime evidence is required for Operational maturity. Evidence: `CarReviewRuntimeEvidencePolicy`, `CarReviewReportCodec`, and `CarReviewRuntimeEvidencePolicySpec` prove an Operational assessment is refused unless its provider-bound, bounded `runtime-observation` Evidence is referenced by an attributable Observation mapped to that capability.
- [x] `P5-55` Integration admits the Textus AI Phase 1 contracts under development for normalized provider/model/mode/purpose/usage/limitation provenance, deterministic CAR Review fixtures, restrictive digest-safe CallTree/metadata, structured output failure, timeout/retry/cancellation behavior, and no implicit provider fallback; missing or incompatible contracts produce an attributable limitation or Unknown and AI output cannot override deterministic findings. Evidence: Textus AI `CarReviewAiRunnerFixture`, `AiExecutionFacts`, and their specifications provide digest-safe purpose/provenance, structured output, retry, failure, and limitation behavior; CBD `CarReviewAiRunnerAdapterSpec`, `TextusAiCarReviewProviderRunnerSpec`, and `CarReviewAssessmentGateBuilderSpec` prove strict metadata admission, incompatible-output Unknown, no fallback, and advisory-candidate gate exclusion.
