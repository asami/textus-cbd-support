# Model Edit cross-view and retained continuation

The same immutable ModelEditSession, ModelEditService and caller authorization
apply in Mono-Koto and Structure contexts. ModelEditCrossView accepts the host's
existing typed Mono-Koto/Structure projections; it does not classify a Use Case or
Slice from a label or invent engineering relationships. Context, component and
exact projected semantic endpoint must match the selected candidate subject.
Existing projection constructors validate supplied DTOs. Candidate/refinement
confirmation, development traces and capability availability still come from the
shared ModelEditViewProjection. Cross-view presentation is not another stored model.

A cross-view operation selects the exact session/candidate represented by its View,
derives a contextual Palette and delegates to ModelEditModelMutation and the same
service. All ordinary authorization, complete command input, explicit successor
reference and external-resolution requirements remain. The resulting View exposes
the existing typed AppliedOperation audit and retained reviews with their current
applicability. It allocates no identity, role or permission. An old View cannot edit
a newer candidate. Abandonment prevents further operations; a fresh caller-declared
session and source candidate are the bounded restart, with no replay or rollback.

Refining a Slice preserves its stable identity and exact independent Specification
and provisional Ticket edge attribution. Candidate/trace/history dependency changes
make a retained old review inapplicable and cannot reuse the old source confirmation
or approval. Display-name similarity supplies neither endpoint equality nor a
resolution observation; only explicitly selected complete evidence can close a
finding. Unsupported source coverage cannot produce a canonical mapping.

## Existing package owners after promotion

`ModelEditCrossView.readPromotion` is a read-only runtime-internal composition of
existing owners. It evaluates the historical package's recorded continuation using
independently supplied request evidence, then captures the current package and
reconstructs canonical continuity through its existing validator. Package identity
and semantic scope must agree. Its result retains both distinct carrier contexts,
the actual historical continuation report and the actual canonical projection.
It writes no cursor and grants no source effects.

The accepted Stage12.7 run has two intentionally different carriers:

- The original complete approved edit package at
  `review-materials/approved-candidate` retains package revision1, its actual
  human-decision-recorded cursor, candidate@10, all nine applied operations, Slice
  record revision2, exact independent Specification/Ticket edges and original source
  dependencies. Existing Rehydration and ContinuationActionGate can reconstruct and
  reevaluate its recorded approved handoff using the separately supplied actual
  review execution basis and Human input. That is historical handoff evidence.
- The active package at the accepted root contains package revision2, explicit new
  realization/continuity/source-snapshot references and the actual promoted r2 source.
  It has no Resume artifact. Existing verifiedContinuation and projection continuity
  admission can inspect it; no current resume action is claimed or synthesized.
  Historical review/approval dependencies are never rebound to this carrier.

The actual Stage12.7 ApplicationReport existed only during application and required
post-validation. Stage12.8 does not recreate it. The retained post-validation JSON
is an observation of the accepted run, not a capability. Current canonical source
can be read against its existing new baseline without reapplying a candidate.
